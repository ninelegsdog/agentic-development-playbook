## Почему этот документ существует

Код в проектах этого портфолио написан AI coding-агентами. Это не повод прятать это —
это повод показать, **что именно делает человек**, когда код пишет машина.

Голое «я попросил модель написать бота» — это не компетенция. Компетенция — это
воспроизводимый процесс, в котором:

- результат не зависит от того, какая модель сейчас доступна;
- ошибка ловится до поставки, а не после жалобы клиента;
- чужой человек может повторить цикл и получить сравнимый результат;
- видно, где проходит граница ответственности.

Ниже — устройство этого процесса. Все цифры — из измеримого состояния репозиториев
на 2026-10-28; коммиты и команды — в [`evidence/metrics.json`](evidence/metrics.json).

## 2. Архитектура harness

```
        БИЗНЕС-ЗАДАЧА
              │
              ▼
    ┌───────────────────────┐
    │ 1. Спецификация (ТЗ)  │  пользовательские сценарии, метрики, scope v1,
    │    отдельный документ  │  UX-контракт, данные, платежи, риски
    └───────────┬───────────┘
                │
                ▼
    ┌───────────────────────┐
    │ 2. Контекст            │  AGENTS.md, CODE_STYLE.md, .env.example,
    │    проектирование      │  контракты, шаблоны ТЗ, релевантные файлы
    └───────────┬───────────┘
                │
                ▼
    ┌───────────────────────┐
    │ 3. Декомпозиция       │  этапы с проверяемым результатом;
    │    задачи              │  флагманский проект задаёт шаблон первым
    └───────────┬───────────┘
                │
        ┌───────┴────────┐
        ▼                ▼
  ┌──────────┐    ┌─────────────┐
  │ Генерация│    │ Ревью кода  │  цикл до зелёных гейтов
  │ (агент)  │───▶│ (человек)   │
  └──────────┘    └──────┬──────┘
        ▲                │
        │                ▼
        └──── ошибки ◀──┴─── ЗАПУСК + ВЕРИФИКАЦИЯ
                                  │
                                  ▼
                          ДЕПЛОЙ / ПРИЁМКА
```

Ключевая идея: **этап без проверяемого результата — не этап.** «Добавить обработчик
заявки» — не этап. «Обработчик принимает анкету, кладёт в БД, админ получает уведомление;
проверка: тест на happy path + на повторный вызов» — этап.

### Что даёт harness

| Без harness | С harness |
|---|---|
| «Попросил модель, получил файл» | результат воспроизводится из спецификации |
| качество зависит от настроения | качество задано гейтами: ruff, mypy, pytest, gitleaks |
| ошибка всплывает у клиента | ошибка ловится тестом до деплоя |
| непонятно, кто автор | роль автора задокументирована и проверяема |

## 3. Принципы работы с контекстом

Контекст — главный расходный ресурс. Правила, которые я применяю:

1. **Контекст — это контракт, а не дамп.** В агент попадает только то, что нужно
   для текущего этапа: контракт, схема данных, стиль, релевантные файлы. Не «вся папка».
2. **Инструкция живёт в репозитории.** `AGENTS.md` и `CODE_STYLE.md` — источник истины
   для агента, а не переписка в чате. Чат забывается, файл — нет.
3. **Состояние передаётся явно.** Между итерациями и между агентами передаётся не «что
   получилось», а список: сделано / не сделано / причина / следующий шаг.
4. **Сжатие вместо повторения.** Длинные логи и история итераций не переносятся в новый
   контекст целиком — переносится вывод и ссылка на артефакт.
5. **Ограничения формулируются как запреты, а не как пожелания.** «Не вызывай
   `FSMContextMiddleware` вручную» работает; «старайся аккуратно с состояниями» — нет.
6. **Контекст перезапрашивается, а не достраивается.** Если агент не знает чего-то —
   это пробел в спецификации, и он чинится там, а не «подумыванием».

### Реальный пример ограничения, а не пожелания

В `CODE_STYLE.md` зафиксирован контракт aiogram, который ломает хендлеры в рантайме,
хотя код выглядит правильно:

```python
# CORRECT — aiogram внедряет FSMContext только в параметр с именем state
async def cmd_admin(message: Message, state: FSMContext) -> None: ...

# WRONG — состояние не придёт, хендлер упадёт
async def cmd_admin(message: Message, state_fsm: FSMContext) -> None: ...
```

Такое правило невозможно вывести из кода — его нужно записать. Это и есть работа
с контекстом: **знание, которого нет в репозитории, агент не получит.**

## 4. Шаблон `AGENTS.md`

Файл, который я создаю в каждом новом проекте:

Полный шаблон — в [`templates/AGENTS.md`](templates/AGENTS.md). Заполняемые поля помечены
`<...>`; разделы «Контракты» и «Где канон» — самые ценные.

Структура:

- `## Роли` — кто решает, кто делает
- `## Стек` — версии и инструменты
- `## Обязательные правила` — стиль, коммиты, секреты
- `## Контракты, которые нельзя вывести из кода` — неочевидные инварианты
- `## Гейты перед коммитом` — команды, которые обязаны проходить
- `## Где канон` — единственный источник истины

Разделы «Контракты» и «Где канон» — самые ценные. Первый закрывает знание, которого
нет в коде. Второй закрывает реальную проблему: копия репозитория на другой машине,
которая молча перестала быть каноном.

## 5. Пример спецификации задачи

Формат ТЗ, по которому сделаны все девять ботов (сокращённый фрагмент):

Полный шаблон — в [`templates/spec.md`](templates/spec.md). Ниже — его скелет (11
разделов):

1. Позиционирование (кому, задача, отличие)
2. Метрики успеха (измеримые результаты)
3. Scope (v1 / v1.1 / вне объёма)
4. Сценарии (пошаговые, с ожидаемым результатом)
5. UX-контракт (типы клавиатур, переходы)
6. Данные (схема, UNIQUE на конфликтах)
7. Платежи (провайдер, идемпотентность)
8. Админка (роли, команды, аудит)
9. Инфраструктура (webhook/polling, health, метрики, бэкапы, секреты)
10. Тесты и приёмка (контрактные тесты, критерии готовности)
11. Риски (что сломается и что делать)

Правило именования v1: **v1 = минимум сложности, v1.1 = докрутка.** Один флагманский
проект пишется первым и задаёт шаблон для остальных — иначе девять проектов
разъезжаются по UX и контрактам.

## 6. Чек-лист ревью AI-кода

Прохожу по нему на каждой итерации. Пункты, помеченные `[gate]`, обязаны быть в CI.
Копия для нового проекта — в [`templates/review-checklist.md`](templates/review-checklist.md).

**Соответствие спецификации**
- [ ] Реализованы ровно те сценарии, что в ТЗ; лишнего не добавлено
- [ ] Критерии приёмки из ТЗ выполнены и проверяемы тестом
- [ ] Каждое «вне объёма» действительно не тронуто

**Корректность**
- [ ] Гонки и конфликты закрыты на уровне БД (`UNIQUE`), а не только в коде
- [ ] Повторный вызов (например webhook) идемпотентен
- [ ] Обработаны пустые значения, лимиты, таймауты
- [ ] Ветки ошибок логируются — «ничего не произошло» недопустимо

**Контракты** *(самый частый источник падений в рантайме)*
- [ ] Все `AGENTS.md` / `CODE_STYLE.md`-контракты соблюдены
- [ ] Имена параметров, от которых зависит внедрение зависимостей (aiogram `state`), совпадают

**Качество**
- [ ] `ruff check .` и `ruff format --check .` — чисто `[gate]`
- [ ] `mypy src/` — без ошибок `[gate]`
- [ ] `pytest` — все тесты проходят, включая существующие `[gate]`
- [ ] Тест умеет падать: удаление строки прод-кода роняет тест
- [ ] Нет мёртвых символов и патчей несуществующих атрибутов в тестах

**Безопасность**
- [ ] Секретов нет в коде, тестах, логах и коммитах `[gate]`
- [ ] `gitleaks` проходит по всей истории `[gate]`
- [ ] Docker: непривилегированный пользователь, `read_only`, `cap_drop: ALL`
- [ ] Входные данные экранируются при рендеринге (в т.ч. в PDF)

**Документация**
- [ ] README соответствует фактическому поведению
- [ ] `.env.example` синхронизирован с кодом чтения конфигурации
- [ ] Присутствует раздел `Development process`

## 7. Чек-лист безопасности секретов

Копия для нового проекта — в [`templates/secrets-checklist.md`](templates/secrets-checklist.md).

- [ ] Секреты только в `.env` (в `.gitignore`) или в зашифрованном виде
- [ ] `.env.example` содержит только имена переменных, без значений
- [ ] `gitleaks` в CI проверяет всю историю, а не только последний коммит `[gate]`
- [ ] Токены Telegram, ключи платёжных систем и webhook-секреты не попадают в:
      - код и тесты,
      - логи и трассировки,
      - сообщения об ошибках в чат,
      - документацию и скриншоты
- [ ] Ключи и `.env.age` не копируются в заметки, базу знаний или переписку
- [ ] Доступы к приватным зависимостям и прода — по отдельным ключам, не по одному «универсальному»
- [ ] Секреты ротируются; есть процедура ротации, а не только намерение
- [ ] Перед публикацией скриншотов и демо проверить, что в кадре нет реальных данных
      (на демо-данных: фейковые имена и телефоны вида `+7 (999) 000-00-00`)
- [ ] Публичный репозиторий собирается **без** доступа к приватным зависимостям,
      либо это явно объяснено в README

## 8. Цикл тестирования и исправления

```
         ┌──────────────────────────────────────────┐
         │                                          │
         ▼                                          │
  спецификация ──▶ генерация ──▶ тесты ──▶ гейты    │
                            │         │             │
                            │         └─ FAIL ──────┘
                            │              │
                            │              ├─ ошибка агента → в контекст: точный текст,
                            │              │   вход, ожидание, факт
                            │              └─ ошибка спецификации → правится ТЗ,
                            │                  а не код
                            ▼
                     ручная проверка поведения
                     (живой бот, не «тест зелёный»)
                            │
                            ▼
                      деплой → smoke → приёмка
```

Правила, которые делают цикл рабочим:

1. **Ошибка возвращается в контекст как факт**, а не как «не получилось, попробуй иначе».
   Формат: вход → ожидание → факт → причина.
2. **Непонятная ошибка — это ошибка спецификации**, пока не доказано обратное.
3. **Зелёный CI не равен работающему продукту.** Гейт покрытия может быть зелёным
   по настройке и красным по факту — проверяйте, а не доверяйте бейджу.
4. **Проверка полного пользовательского пути:** клиент → Telegram → бот → ответ.
   «Контейнер healthy» — это прокси-сигнал, а не доказательство.
5. **Тест обязан уметь падать.** Тавтологии удаляются: тест, который не может
   упасть, хуже отсутствия теста — он создаёт ложную уверенность.

### Честная оговорка о покрытии

Гейт покрытия в публичных репозиториях выставлен на 70–90 % (у бота `membership`
— 90 %) [E:coverage.gate]. На 2026-10-28 все девять ботов проходят свои гейты: измеренное покрытие
71,7–92,2 % [E:coverage.range]. На коммитах публикации (до 2026-10-03) восемь из девяти показывали
72,7–92,9 % [E:coverage.publication]; у девятого в той среде не собрались тесты, что не равно низкому
покрытию.

Раньше здесь стояло «измеренное покрытие около 32 %». Это число не воспроизводится
запуском тестов: оно получается из `pytest --collect-only`, который импортирует
модули, но не выполняет тесты, и потому pytest-cov считает покрытие почти пустым
(26,46 % у `bookingbot`, например) [E:coverage.collect_only]. Ошибка была в способе измерения, а не в коде
ботов. Команда, коммиты и сырые результаты — в
[`evidence/README.md`](evidence/README.md).

## 9. Передача контекста между агентами

Когда работу делят между агентами (или между итерациями), передаётся **handoff**, а не
переписка:

Полный шаблон — в [`templates/handoff.md`](templates/handoff.md). Формат:

```text
## Handoff
**Задача:** <одно предложение>
**Статус:** сделано X из Y
### Сделано / ### Не сделано и почему / ### Найденные ограничения / ### Проверка / ### Следующий шаг
```

Правила:

- handoff пишется **в том же репозитории**, а не в чате;
- каждый пункт проверяем или явно помечен как непроверенный;
- «частично» без указания, что именно осталось, — запрещённая формулировка;
- если агент сменился, а handoff нет, работа считается потерянной независимо от
  состояния файлов.

## 10. Что я не утверждаю

Честность здесь — часть метода, а не скромность.

- Я **не** утверждаю, что писал каждую строку этих проектов руками. Код производили
  AI coding-агенты; моя работа — спецификация, контекст, декомпозиция, гейты,
  ревью, деплой и результат.
- Я **не** выдаю число, полученное `pytest --collect-only`, за измеренное покрытие:
  цифра должна воспроизводиться запуском тестов, иначе это не измерение.
- Я **не** привожу независимого подтверждения, что боты отвечают прямо сейчас:
  `t.me`-ссылки и health-проверки из среды, где готовился этот текст, недоступны.
  Зелёный deploy-run — это E2 (образ собран и запушен), а не доказательство живого
  ответа.
- Я **не** обещаю «бот без ошибок». Обещаю согласованный объём, критерии приёмки и
  ответственность за поставку.
- Я **не** продаю «промпты». Продаётся работающий бот на вашем сервере, документация
  и сопровождение.
- Публичные репозитории зависят от общей библиотеки `botkit-core` — она тоже
  публичная, поэтому публичный репозиторий собирается без доступа к приватным
  зависимостям.
