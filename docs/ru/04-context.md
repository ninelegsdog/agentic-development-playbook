# 3. Принципы работы с контекстом

Контекст — главный расходный ресурс. Правила, которые я применяю:

1. **Контекст — это контракт, а не дамп.** В агент попадает только то, что нужно
   для текущего этапа: контракт, схема данных, стиль, релевантные файлы. Не «вся папка».
2. **Инструкция живёт в репозитории.** `AGENTS.md` и `CODE_STYLE.md` — источник истины
   для агента, а не переписка в чате. Чат забывается, файл — нет.
3. **Состояние передаётся явно.** Между итерациями и между агентами передаётся не «что
   получилось», а список: сделано / не сделано / причина / следующий шаг.
4. **Сжатие вместо повторения.** Длинные логи и история итераций не переносятся в новый
   контекст целиком — переносится вывод и ссылка на артефакт.
5. **Ограничения формулируются как запреты, а не как пожелания.** «Не вызывай
   `FSMContextMiddleware` вручную» работает; «старайся аккуратно с состояниями» — нет.
6. **Контекст перезапрашивается, а не достраивается.** Если агент не знает чего-то —
   это пробел в спецификации, и он чинится там, а не «подумыванием».

## Реальный пример ограничения, а не пожелания

В `CODE_STYLE.md` зафиксирован контракт aiogram, который ломает хендлеры в рантайме,
хотя код выглядит правильно:

```python
# CORRECT — aiogram внедряет FSMContext только в параметр с именем state
async def cmd_admin(message: Message, state: FSMContext) -> None: ...

# WRONG — состояние не придёт, хендлер упадёт
async def cmd_admin(message: Message, state_fsm: FSMContext) -> None: ...
```

Такое правило невозможно вывести из кода — его нужно записать. Это и есть работа
с контекстом: **знание, которого нет в репозитории, агент не получит.**
